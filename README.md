# Brainrot of the AI - BotA

[Open the character gallery](GALLERY.md) — every generated character in one grid.

Design docs for the 24-hero roster: characters, kits, mechanics, art, tone and spec.

Use the navigation. Numbers and cross-hero hooks marked UNVERIFIED or GUESS are unverified.

Character prompts: characters/STYLE.md holds the shared lead and tail. Each characters/NNN-*.md holds its subject and hook. Run `node tools/sync-roster.mjs` after editing them; it regenerates roster.yaml, characters/INDEX.tsv, each file's Card section, and the signature gags in plan/15. Run `node tools/sync-roster.mjs --check` before committing.

Gallery: `node tools/build-gallery.mjs` rebuilds GALLERY.md and the gallery images from the character source images, adds the gallery to manifest.json and the README link when missing. The repo root comes from the script's own path, so any working directory works. The image inputs live outside this repo and are set with BOTA_CHARS_DIR (default ../chars), BOTA_GENERATED_DIR (default ../characters/memes/generated) and BOTA_PYTHON (default python3, which must provide PIL for tools/resize.py). Without any source images the script exits 2 instead of writing an empty gallery.

Prop manifests: a bare `node tools/verify-props.mjs` runs the host-free file:// self-test and prints a SKIPPED line; `node tools/verify-props.mjs --manifests docs/bota-props-2026-11-06.json docs/bota-props-explicit-2026-11-06.json` checks both manifests offline against the GLBs (magic, version, declared length, bytes, sha256, jobId, responseJson). The committed manifests carry absolute paths to GLBs that live only on the generating host, so the real-manifest check needs those GLBs and is never run by default. `node tools/verify-props.mjs --self-test` runs only the forced-failure witnesses. No network, no `.env`, no regeneration.

Held prop rows: docs/bota-ambiguous-resolution.md records the owner's decisions for all 16 ambiguous rows (A3, B2, C3, C2, D1 and the two one-mesh decisions), each with 0 new GLBs; the [fast-path dry run](/tmp/hy3d-bota-held-fast-path-dry-run.md) lists the exact rows. No generation is implied by these decisions.
Implementation export: `export/` contains machine-readable hero, kit, voice and image-reference data keyed by oscraft three-letter acronyms. `export/` is the legacy 26-key machine handoff: it keeps the retired `002`/`011` rows as evidence under `internal/retired-character-cards/` and `internal/retired-gallery/`, while this repo's active roster, gallery and design docs are 24 heroes and 25 images. Run `python3 tools/validate-export.py`; it parses JSON/YAML/TSV, checks source lines and paths, verifies SHA256 sums, and rejects stale names or old slugs as identifiers.
Decision layer: `export/decisions.json` groups every GUESS/UNVERIFIED/AMBIGUOUS marker into stable decisions with sources, options, confidence and field paths. `export/DECISIONS.md` is the readable form. Run `python3 tools/validate-export.py --decisions` to prove marker coverage.
Integration contract: `export/INTEGRATION.md` and `export/integration-contract.json` define the engine handoff; `export/conformance.json` pins counts, hashes and required presence. Run `python3 tools/validate-export.py --integration` to check the contract against the live export. `GUESS`/`UNVERIFIED`/`AMBIGUOUS` values remain decision-gated and must not be promoted to canon.
Live integration: `python3 tools/validate-integration-live.py` performs a read-only cross-project check of `/workspace/oscraft/scenarios/bota/` against the export. It supports `--identifier-mode acronym` (historical) and `--identifier-mode bota-fullname --default-dota-acronyms` (oscraft's new target). It reports `UNAVAILABLE` for transient unreadable files and `DRIFT` for real mismatches with exact paths; it never writes to oscraft.
Engine-data build: `python3 tools/build-engine-data.py` writes a deterministic, contract-safe `export/engine/` view; `python3 tools/validate-engine-data.py` validates it. Owner-decision, intentionally-open, and marked values stay `null` with decision provenance and `do_not_promote: true`; recommendations are never promoted.
Decision packet: `export/DECISION-PACKET.md` and `export/decision-packet.json` make the 425 null-gated engine fields owner-actionable without promoting values. Use `python3 tools/validate-decision-packet.py`; `tools/apply-decision.py` defaults to dry-run and writes only opt-in overlays to `export/engine-resolved/`.
Apply audit: `export/APPLY-GUIDE.md` documents the strict opt-in apply/revert commands. `python3 tools/validate-apply-mechanism.py` tests dry-run, confirmed apply, refusal cases, audit records, canonical immutability, and temp cleanup; the real `export/engine-resolved/` is not created.
Pipeline: `bash tools/check-bota-export.sh` is the single verification/build entrypoint; `python3 tools/check-bota-export-clean.py` proves the same pipeline from a clean no-`.git` temp workspace and compares generated engine files byte-for-byte.
Status watch: `python3 tools/bota-export-watch.py` runs the pipeline once and writes `export/export-status.json`; `python3 tools/validate-export-status.py` validates that snapshot. `export/STATUS.md` records the current verified state and exact commands.
Spawn compatibility: `export/SPAWN-COMPATIBILITY.md` is a read-only cross-project verdict for `/workspace/wscheppity`; `python3 tools/validate-spawn-compatibility.py` checks counts, evidence lines, BOTA hashes, decision gates, and proves wscheppity status is unchanged. The verdict is `reusable-data`, not same-game or live integration.
Coordinated iteration: hy3d owns all content, first with pooled emails and then with the relay. BOTA owns rules and reads `/workspace/hy3d/output/content-for-bota.json` before each pass. `python3 tools/build-rule-demand.py` publishes `export/rule-demand.json` / `.tsv`; `python3 tools/validate-rule-demand.py` checks coverage, identifier hygiene, no invented asset paths, and real hy3d SHA-256 evidence. `plan/33-coordinated-content-rule-iteration.md` records the iteration rules, Receipt/Repost/Camera chains, ambiguity resolutions, and identifier inversion.

Request queues: `python3 tools/build-rule-demand-v2.py` resolves the prior `requested`/`blocked` rows into six states and publishes `export/content-request-queue.json` / `.tsv` for hy3d plus `export/spawn-extraction-gaps.json` for wscheppity. `python3 tools/validate-request-queues.py` proves exact prior-row reconciliation, stable IDs, actor/citation/evidence/acceptance criteria, no invented hashes, and SHA-256 coverage. Outputs are read-only toward peers.

Live coordination watcher: `python3 tools/watch-coordinated-queues.py --once` recomputes all content/extraction queue rows from live hy3d, wscheppity, extra and oscraft evidence, writing only `export/coordination-status.json` / `.md`. The default is bounded (10 minutes, 10 s poll). `python3 tools/validate-coordination-status.py` validates live counts, evidence, identifiers and gates. `export/owner-decision-brief.md` gives neutral options for the two gated rows and promotes nothing.

Coordination auto-refresh: `python3 tools/auto-refresh-coordination.py --once` rebuilds the live demand/queues when hy3d, wscheppity, extra or oscraft manifests change, then runs the full validator set. Default mode is bounded (10 minutes, 10 s). `python3 tools/validate-auto-refresh.py` proves the record, hashes, status, gates and peer read-only behavior. See `export/AUTO-REFRESH.md`.

Owner progress dashboard: `python3 tools/build-progress-dashboard.py` reads peer evidence and writes `export/progress-dashboard.json` / `PROGRESS-DASHBOARD.md` plus `export/actor-backlog.json` / `actor-backlog.md`. `python3 tools/validate-progress-dashboard.py` proves cited paths, counts, no orphan rows, gates, hashes and `STALE=false`. `extra` mid-rebuild state degrades as `UNAVAILABLE`; no value is promoted.
